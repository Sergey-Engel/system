# План реализации мониторинга связности VPN

## Результат

Развернуть на Mac локальный мониторинг текущего рабочего маршрута через
AmneziaVPN/AmneziaWG на Fornex:

```text
Mac host probes -> Prometheus -> Grafana
```

Система должна опрашивать цели каждые 10 секунд, сохранять историю минимум 30
дней и показывать, какой слой связи отказал во время очередного перерыва.

## Ограничения

- На первом этапе не менять MikroTik, TimeWeb, Cenuta, Fornex и VPN-конфиги.
- Рабочий Fornex AmneziaVPN не отключать во время установки.
- Проверки выполнять с Mac, а не только из Docker-сети.
- Не сохранять private keys, preshared keys, QR-коды и полные `.conf` в
  Obsidian или в dashboard.
- Реализацию выполнять короткими шагами: после каждого шага проверять
  результат и только затем переходить дальше.

## Этап 0. Зафиксировать baseline

**Действия:**

1. Зафиксировать, что Mac в момент установки работает через Fornex
   AmneziaVPN/AmneziaWG; текущий внешний IP `103.75.126.143`.
2. Выбрать активный `site_profile`:
   - `orekhovo_asarta`: Орехово, Asarta, gateway `192.168.88.1`, последний
     известный IP Mac `192.168.88.20`, Wi-Fi;
   - `nakhimova_domru`: Нахимова 11, Дом.ру, gateway `192.168.88.1`, последний
     известный IP Mac `192.168.88.28`, Ethernet.
3. Получить текущий IP Mac динамически средствами macOS; значения из таблицы
   использовать только как справочные.
4. Записать текущий внешний IP и активный маршрут.
5. Проверить отдельно gateway, ICMP, DNS и HTTPS вручную.
6. Отметить время начала baseline.

**Результат:** понятен исходный маршрут и есть контрольная точка для сравнения.

**Критерий перехода:** все проверки выполнены или явно отмечены как
недоступные; причина недоступности записана.

Профиль передается exporter через конфигурацию или переменную окружения. Он
должен присутствовать в label каждой probe-метрики, чтобы историю одной
площадки нельзя было принять за историю другой площадки с тем же gateway.

## Этап 1. Подготовить каталоги и Docker volumes

**Действия:**

1. Выбрать каталог в Dropbox System для данных мониторинга и compose-файлов.
2. Создать отдельные persistent volumes для Prometheus и Grafana.
3. Проверить права доступа и отсутствие синхронизации секретов в Obsidian.
4. Подготовить `.gitignore` или аналогичное правило для локальных credentials.

**Предлагаемое расположение:**

```text
services/monitoring/vpn-connectivity/
├── compose.yaml
├── prometheus/
│   └── prometheus.yml
├── grafana/
│   └── provisioning/
├── probe/
└── evidence/
```

Каталоги создаются только при переходе к реализации. На этапе подготовки этого
плана файлы и сервисы не создавались.

## Этап 2. Реализовать host probe agent

**Действия:**

1. Создать небольшой локальный exporter без секретов.
2. Запустить его на `127.0.0.1:9105`.
3. Задать таймауты, чтобы один зависший тест не блокировал остальные:
   - gateway/ICMP: до 3 секунд;
   - DNS: до 3 секунд;
   - HTTPS: до 5 секунд.
4. Добавить метрики `up`, latency, duration и error counters.
5. Добавить timestamp последнего успешного измерения.
6. Для WireGuard получать только handshake age и counters, без вывода ключей.
7. Добавить динамическое определение текущего LAN IP и интерфейса Mac.
8. Добавить label `site_profile` и ограниченный CSV/JSON export для incident
   evidence.

**Критерий перехода:** endpoint `/metrics` отвечает локально, значения меняются
примерно каждые 10 секунд, а exporter не содержит секретов.

## Этап 3. Подключить Prometheus

**Действия:**

1. Создать минимальный `prometheus.yml`.
2. Настроить scrape target `host.docker.internal:9105`.
3. Установить `scrape_interval: 10s`.
4. Задать retention `30d`.
5. Запустить Prometheus с постоянным хранилищем.
6. Проверить страницу targets и отсутствие пропусков scrape.

**Критерий перехода:** Prometheus видит exporter как `UP`, а запросы возвращают
ряд значений минимум за несколько минут.

## Этап 4. Подключить Grafana

**Действия:**

1. Запустить Grafana с постоянным хранилищем.
2. Ограничить публикацию портов localhost.
3. Добавить Prometheus как единственный источник данных первой версии.
4. Создать dashboard с четырьмя панелями:
   - Connectivity state;
   - Latency;
   - Failure matrix;
   - WireGuard handshake/TX/RX.
5. Добавить переменную временного диапазона.
6. Сохранить dashboard в provisioning или в экспортируемый JSON без секретов.

**Критерий перехода:** dashboard отображает минимум 15 минут истории и
различает успешные и неуспешные проверки.

## Этап 5. Настроить правила предупреждений

Первая версия должна быть консервативной, чтобы не создавать шум:

- warning: один неуспешный цикл;
- incident candidate: две или три последовательные ошибки, то есть примерно
  20–30 секунд;
- critical: одновременно отказали HTTPS и DNS или устарел WireGuard handshake.

Уведомления сначала можно оставить только в Grafana. Внешние уведомления
добавлять после проверки качества метрик.

**Критерий перехода:** искусственный тестовый отказ одного probe вызывает
ожидаемое состояние и не маскируется усреднением.

## Этап 6. Контролируемая проверка

**Действия:**

1. Оставить Mac подключенным через Cenuta WG.
2. Наблюдать dashboard минимум 60 минут.
3. При очередном реальном сбое записать время начала и конца.
4. Сопоставить состояние gateway, ICMP, DNS, HTTPS и WireGuard.
5. Сохранить короткий evidence-фрагмент за 5 минут до и после события.
6. Сравнить событие с серверными handshake/counters TimeWeb и Cenuta.

**Критерий результата:** можно ответить, был ли сбой локальным, полным,
только прикладным или специфичным для UDP/WireGuard.

## Этап 7. Эксплуатация

После успешной проверки:

- закрепить compose и конфигурацию в Dropbox System;
- добавить короткую инструкцию запуска/остановки в этот документ или Quick
  Guide;
- настроить резервное копирование только конфигурации мониторинга и
  dashboard, без credentials;
- периодически удалять старую evidence-историю, если она больше не нужна;
- при изменении рабочих VPN сначала проверять, что мониторинг продолжает идти
  через нужный маршрут.

## План отката

Откат не затрагивает VPN-систему:

1. остановить только контейнеры Grafana/Prometheus;
2. остановить host probe agent;
3. сохранить последний evidence export;
4. удалить или переименовать только каталог мониторинга, если он поврежден;
5. убедиться, что рабочий Cenuta WG и обычный интернет не изменились.

## Приемочные проверки

| Проверка | Ожидаемый результат |
| --- | --- |
| Интервал | новые точки примерно каждые 10 секунд |
| LAN | gateway определяется отдельно от внешнего интернета |
| DNS | DNS-ошибка не маскирует рабочий HTTPS по IP |
| HTTPS | виден рабочий прикладной TCP/TLS-доступ |
| WG | видны handshake age и изменение counters без ключей |
| История | доступны 15 минут, 1 час и 24 часа |
| Сбой | 20–30-секундный провал виден как отдельное событие |
| Маршрут | probe выполняется с Mac через активный Cenuta WG |
| Безопасность | секреты отсутствуют в Obsidian, dashboard и metrics |
| Откат | остановка мониторинга не влияет на VPN |

## Следующий шаг после утверждения

Реализацию начинать с Этапа 0. На каждом шаге выдавать одну команду или одно
действие, дождаться результата и только после проверки переходить дальше.
